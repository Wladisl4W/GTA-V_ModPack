# Соглашения GTA V ModPack

Эти правила применяются к новому коду и к модулям при их поэтапной переработке. Они не требуют немедленно переименовать существующие классы, файлы или данные. Текущее расположение описано в [`STRUCTURE_RU.md`](STRUCTURE_RU.md), соответствие игровых меню и исходников — в [`MENU_CODE_RU.md`](MENU_CODE_RU.md), переход имён — в [`NAMING_MAP_RU.md`](NAMING_MAP_RU.md), образец страницы модуля — в [`MODULE_TEMPLATE_RU.md`](MODULE_TEMPLATE_RU.md).

## Имена и границы модулей

- Один технический ID на модуль: английский `PascalCase` без пробелов, например `Camera`, `Paint`, `Wildlife`. Вносить его и каждый игровой `.cs` в [`development/registry/modules.json`](../development/registry/modules.json). ID означает владельца кода и данных, а не заголовок окна.
- Для игрока использовать короткое русское название по действию. Название, подпись клавиши и описание верхнего игрового меню задавать в `scripts/ReloaderPlugins/Plugins/_System/Shared/Code/ModuleMenus.cs`; F5 и заголовок меню читают их оттуда. Названия внешних форматов, native API, моделей и клипов сохранять техническими.
- Плагин отвечает за одну понятную область функций. Перед разделением большого модуля выяснить владельца настроек, меню, контроля ввода и состояния. `Paint` и `Wildlife` пока остаются едиными модулями; вопрос их разделения записан в карте названий.

## Код C# и файлы

- Типы, пространства имён, свойства и публичные методы — `PascalCase`; параметры и локальные переменные — `camelCase`; приватные поля — `_camelCase`; константы — `PascalCase`. Булево имя должно выражать состояние или вопрос (`_isLoading`, `CanStart`).
- Имя файла соответствует основному типу. Если один класс разделён по функциям, использовать `ClassName.Feature.cs`, например `PaintPlugin.Presets.cs`. У отдельного сервиса файл носит имя сервиса. Пространство имён игрового модуля — `ModPack.<ID>`; общий код — `ModPack.Core`. Интерфейс `IGtaPlugin` остаётся глобальным, поскольку загрузчик находит его по имени через отражение.
- Внутри `scripts/ReloaderPlugins/Plugins/<меню>/Code` размещать `.cs` по смысловым разделам: `VehicleSwap`, `Wildlife`, `Streamer` и т. д. У каждого раздела с сохраняемыми файлами одноимённая папка под `Data`. Относительный путь исходника указывать в `development/registry/modules.json`; загрузчик читает `.cs` во вложенных `Code`.
- Имена методов описывают действие, а имена состояний — состояние. Прямые числа с игровым смыслом выносить в именованные константы с единицей измерения (`LoadTimeoutMs`, `SearchRadiusMeters`). Не создавать дополнительный класс или слой только ради одинакового размера файлов.
- Комментарий объясняет неочевидную причину, ограничение GTA/native API или условие совместимости. Очевидный вызов метода комментировать не нужно. Публичные контракты, сложные переходы состояний и формат сохраняемых данных документировать рядом с реализацией.

## Тексты в GTA

- Верхние заголовки меню совпадают с F5 через `ModuleMenus.cs`. `development/registry/modules.json` описывает технические модули сборки и может содержать более широкие имена, когда один плагин обслуживает несколько игровых меню.
- Для одного действия использовать одни слова: «случайная покраска», «загрузка педов», «настройки следования». Короткие пункты меню пояснять в описании. Цветовые коды `~g~`, `~r~` и другие не переводить.
- Оставлять технические имена там, где они помогают вводу или поиску: Object Spooner, Menyoo, FOV, NPC, имена моделей и файлов. Ошибки игроку писать по-русски; диагностические сообщения могут оставаться на английском.

### Порядок и цвета пунктов меню

- В редакторе пресета сначала ставить галочку действия, сразу под ней — его параметры. Параметры доступны и при выключенной галочке: их можно подготовить до включения действия. Если параметров нет, добавлять пустой пункт не нужно.
- `~g~` — подтверждающее действие: создать, сохранить, применить. `~r~` — удаление и сброс с потерей данных; подтверждение удаления тоже красное. `~b~` — переход к настройке, списку или редактированию. Цвет относится к действию, а не к модулю.
- Обычные галочки, значения и названия сохранённых элементов оставлять без цветового кода. Если цвет уже обозначает игровой объект или состояние (например, цвет краски или маркер), сохранять его смысл и не подменять общим цветом действия.
- Вложенный параметр размещать сразу после родительской галочки с небольшим отступом в названии. Настройки внутри подменю группировать в том же порядке, в каком они применяются. Не использовать цвет как единственный признак: название пункта должно объяснять действие.
- Применять правила ко всем модулям при изменении их меню; при переработке меню проверять старые цветовые обозначения и сохранять их игровой смысл.

### Единый шаблон игрового меню

- Заголовок — короткое русское имя функции, подзаголовок — контекст (выбранный объект, текущий пресет или этап). Один пункт выполняет одно действие; меню не должно смешивать настройки выбранного объекта и массовые операции без отдельного подменю.
- Сначала показывать основной запуск или выбор сохранённого элемента, затем связанные галочки и параметры, затем управление списками и сохранением, в конце опасные действия. Для нескольких независимых функций создавать подменю с понятными именами, сохраняя возврат на один уровень назад.
- Переключатель обозначает длительное состояние или включение действия; кнопка — разовое действие; пункт перехода открывает подменю. Параметр располагается сразу под своей галочкой и остаётся доступен, пока галочка выключена. Списки моделей показывают добавление первым пунктом, затем содержимое и явное удаление.
- У каждого пункта должно быть короткое понятное название. В описании указывать, что выбрано и где выполняется действие, когда это не видно из названия. При недоступном действии показывать причину, а после выполнения — краткий результат. Названия и порядок проверять в игре, поскольку длина строк и возврат по Esc зависят от LemonUI.
- Цвета из раздела выше одинаковы во всех модулях. Красным оформлять само удаление и его подтверждение; обычное исключение модели из редактируемого списка также красное. Дефолтные элементы и игровые состояния могут иметь собственный цвет, если смысл подписан текстом.

## Данные, ошибки и диагностика

- Каждый модуль владеет своими настройками, сохранениями и журналами в `scripts/ReloaderPlugins/Plugins/<ID>/Data`. Получать путь через `ModPack.Core.PluginStorage`, когда это предусмотрено для данного файла; не писать новые данные в корень `ReloaderPlugins`. Папку создавать при первом обращении. Для Camera пути находятся в `Data/Saves/Paths`; общий журнал ошибок — в Core.
- Существующие имена `ModdedCamera`, `RainbowPaint`, `SharkRider` и другие ключи `PluginStorage`, имена JSON/INI и поля сохранений являются совместимыми идентификаторами. Русский заголовок меню может измениться отдельно; ключ данных — только с миграцией, резервной копией и тестом повторного запуска.
- Ловить ошибку на границе внешнего файла, native API, загрузки модели или операции плагина. В журнале указывать модуль, действие, путь или идентификатор без лишнего содержимого файла, причину и исключение. Не скрывать сбой пустым `catch` и не писать одно и то же исключение каждый игровой кадр. Пользователю показывать краткое понятное состояние, детали оставлять в журнале.
- Не менять файлы Menyoo и AddonPeds в ходе перестройки. Интеграции читают их как внешние данные; изменение избранного Ped Importer выполняет только по отдельной команде пользователя.

## Документация и проверка

- У каждого игрового меню и подраздела есть README рядом с кодом в `scripts/ReloaderPlugins/Plugins`. Подробное описание модуля находится в `docs/modules/<ID>.md`, профильные тесты — в `development/tests/<ID>`. Общие правила и обзор остаются в `docs`, машинные сведения — в `development/registry/modules.json`.
- README сначала объясняет игроку запуск и действия, затем разработчику данные, зависимости, исходники и проверку. Указывать реальное ограничение и статус проверки: сборка, доставка, загрузка Reloader и поведение в GTA — разные подтверждения. Если раздел неприменим, написать «Нет» с короткой причиной.
- Генератор карты создаёт лишь начальный README для нового ID и не перезаписывает существующий. После генерации заполнить его по шаблону вручную; не считать автоматически созданный текст законченной документацией.
- Для игрового изменения выполнить `modpack.cmd Check`, соответствующие узкие тесты и при установке сверку копий; для визуального поведения нужна проверка в GTA. Для документации сверить ссылки, ID и пути через `development/build/build-project-map.ps1 -Check`. Публикация, коммит и обновление загрузчика — отдельные действия.
